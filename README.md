# 3AS · 3D Annotation System

**3D 模型预处理与注释系统**  
用于 GLB 模型的元数据提取、材质/贴图/网格块分析、注释标记与导出

---

## 概述

3AS（3D Annotation System）是一个浏览器内运行的 GLB 模型预处理工具，提供：

- **四张完整表格**：材质（PBR）、贴图（含格式/尺寸/字节数）、模型块（网格/顶点/TRS）、场景元数据
- **实时 3D 预览**：拖拽旋转查看模型，金色边框 + 网格辅助
- **注释持久化**：材质/贴图备注、节点别名/显隐/编辑权限、整档备注，存 localStorage，可导出 JSON
- **后端（可选）**：PHP 服务，「打开 GLB → 从服务器打开」「另存为 GLB → 保存到服务器」，支持 GLB 上传/多项目列表/项目详情拉取（见 `Doc/BACKEND-SPEC.md`），本地功能不依赖它
- **未来扩展**：注释版本历史 UI、更新已有项目（覆盖上传）、账号系统

**适用场景**：
- 为项目 GLB 编写元数据说明（材质命名、贴图用途、节点分组）
- 检查模型质量（顶点数、贴图格式、扩展支持）
- 准备查看器配置（默认显隐、中心点、包围盒）
- 交付注释 JSON 给开发团队或查看器

## 快速开始

3AS 分两层：**本地功能完全不依赖后端**（打开本地 GLB、编辑注释、另存为本地 GLB、导出注释 JSON），只有「从服务器打开」「保存到服务器」这两项才需要额外起一个 PHP 服务。只用本地功能的话，跳过下面「后端服务器」那一段即可。

### 本地运行（静态页面，本地功能足够用）

```bash
cd 3as
python -m http.server 8000
# 访问 http://localhost:8000
```

**依赖**：无需构建，纯静态 HTML + ES 模块，复用 `vendor/` 内的 three.js 0.166.1

### 后端服务器（仅「从服务器打开」/「保存到服务器」需要）

后端是 PHP（见 `Doc/BACKEND-SPEC.md`），本机测试推荐**用同一个 PHP 内置服务器同时托管静态页面和后端 API**（合并成一个源，最简单、不需要处理跨源 CORS）：

```bash
cd 3as
php -S 127.0.0.1:8000 -t .
# 访问 http://localhost:8000，静态页面和 server/api/*.php 都在这一个源下面
```

如果坚持要静态页面（Python）和后端（PHP）分开跑成两个进程，也可以，但那样前端 fetch 后端接口会跨源，PHP 那边要自己加 CORS 响应头（`Access-Control-Allow-Origin` 等）——`server/api/*.php` 目前没有内置这层，图省事就用上面「同一个 PHP 服务器」的方案。

部署到真实服务器（Apache/PHP-FPM）时同理：只要 `index.html` 和 `server/` 目录在同一个域名/端口下，「从服务器打开」「保存到服务器」用的都是相对路径 `server/api/...`，不需要额外配置就能工作。

### 加载模型

1. **拖拽**：将 `.glb` 文件拖入视窗中央虚线框
2. **打开 GLB ▾**：点击右上角「打开 GLB」展开下拉菜单——「本地文件」跟原来的「打开 GLB」按钮完全一样（不依赖后端）；「从服务器打开」弹出项目选择列表（需要后端服务器已启动，见上面「后端服务器」一节）

加载后：
- 左侧显示实时 3D 预览（可旋转/缩放）
- 右侧面板显示四个标签页：材质 / 贴图 / 模型块 / 场景
- 底部状态栏显示「预处理完成（已恢复历史注释）」或「预处理完成」
- 「模型块」Tab 是上下分栏布局——上方选中节点详情区有「⧉ 样例复制」（创建样例复制）「⬚ 包围盒」两个操作按钮（2026-08-07 `Doc/TODO.md` #36：原来这里的「⇩ 导出」按钮去掉了，导出选中节点改从视口右侧工具条 `⇩` 按钮触发，避免两处重复入口；「✥ 移动/旋转」2026-08-06 起已经改成详情区内联 T/R/S 输入框，不再是独立按钮），下方是精简树状列表（单子节点组自动合并显示），详见下方表3说明

## 多模型（同时加载多个 GLB）

对应 `Doc/EDITOR-SPEC.md` §18、`Doc/TODO.md` #39/#40。**3AS 不再是「一次只能编辑一个 GLB」的工具**——可以同时加载多个 GLB 文件，在同一个视口里合成显示并精确对齐，这是为「一个大场景本来就是拆成多个 GLB 文件分别导出，要在这个工具里拼回一个完整场景」这个真实需求做的。

- **累加加载，不是替换**：把 `.glb` 文件拖入视口（支持**一次拖入多个文件**，也支持分多次拖入）、或者用「打开 GLB ▾ → 本地文件」，都是**追加**一个新模型进当前场景，不会清空已经加载的模型。第一个加载的模型自动成为「正在编辑」的模型；后续加载不会自动切走正在编辑的模型（避免正在编辑时被意外打断），除非当前一个模型都没有。
- **「重新载入 GLB」语义不变**：场景菜单「重新载入 GLB」仍然是原地刷新当前正在编辑的这一个模型（清空它的运行时状态重新解析），不会新增模型条目——这条入口跟「累加加载」是两回事，为「3ds Max 那边模型改了重新导出一版」这个场景准备。
- **模型切换器**：header 顶部新增「模型 (N) ▾」下拉菜单（加载模型后才出现），列出全部已加载模型，当前正在编辑的那个带 `●` 高亮。点某一项即可切换——切换后材质/贴图/模型块/场景四个面板整体刷新成这个模型的数据，视口同时仍然渲染全部已加载模型（不只是正在编辑的这一个）。
- **完全隔离**：每个模型各自独立一份材质/贴图/模型块数据、撤销栈、操作脚本、测量基点、包围盒标注——编辑 A 模型（改材质颜色、生成包围盒、新增基点……）完全不会影响 B 模型的数据，切换回 A 后编辑状态原样保留。
- **基点对齐（`Doc/TODO.md` #40）**：加载第二个及以后的模型时，如果这个新模型自己也有测量基点、且场景里已经有别的带基点的模型，会弹出「对齐到已加载模型」选择器——手动选一个已加载模型 + 它的一个基点 + 新模型自己的一个基点（**不做按名字自动配对猜测**，避免猜错导致对齐到错误位置这种不容易第一时间发现的错误），点「对齐」后新模型会整体平移旋转，让两个基点的世界坐标+朝向精确重合；点「跳过」则维持默认摆位（原点重叠）。算法是标准的"给定一对锚点重合反解相似变换"（无缩放项），经手写独立代数校验精度到 1e-15（浮点噪声量级）；新模型没有基点时不会弹窗，直接沿用默认摆位。对齐偏移量存在每个模型独立的「放置容器」变换里，不影响模型自身内部的坐标系（跟 `preprocess()` 的视口归一化缩放分层，互不干扰）。

## 场景菜单

Header 最左侧有一个「场景 ▾」下拉菜单按钮，跟右侧那一排功能按钮（打开 GLB / 导出注释 JSON / 另存为 GLB / 日志）区分开——点击展开子菜单，而不是直接触发动作。点击菜单外部区域或按 ESC 都会收起。「打开 GLB」「另存为 GLB」也是同一套下拉交互（见下方「头部菜单：打开 GLB / 另存为 GLB」一节），三个菜单共享同一份 CSS/JS 基础设施（`registerMenu()`），行为完全一致。

「模型」子菜单分组里有两项：

- **重新载入 GLB**：点击后重新打开文件选择对话框，选中一个 GLB 文件（可以是同一个文件，也可以是新版本文件）后按现有「打开 GLB」同一套流程（`openBuf()` → `preprocess()`）完整重新加载——**不是**恢复到当前文件的原始状态，而是清空当前全部运行时状态（材质编辑、包围盒等）重新走一遍解析；但**不清空操作脚本**（选同一个文件时 `anno.script` 会经 `localStorage` 自动接上，见下方「操作脚本记录 + 重放系统」）。这是为「3ds Max 那边模型改了重新导出一版，要在 3AS 里重新走一遍标注」这个场景准备的入口。
- **重放操作脚本**：读当前 `anno.script`，重放前先做一次节点/材质名称差异梳理，逐条重新执行脚本里记录的编辑操作。详见下方「操作脚本记录 + 重放系统」一节。

实现过程中发现并修复了一个真实的浏览器坑：原生 `<input type="file">` 重新选中「路径和内容都跟上次一样」的文件时不会触发 `change` 事件（Playwright 实测确认，包括内容字节真的改过但路径没变的情况）——这正好命中「重新载入 GLB」最主要的使用场景（用户覆盖导出到同一路径）。修复方式是在弹出文件对话框之前先把 `fileInput.value` 清空，让浏览器认为下一次选择总是「新的」，「打开 GLB」按钮也一并做了同样的修复。

## 头部菜单：打开 GLB / 另存为 GLB

`Doc/TODO.md` #21 把原来平铺的「打开 GLB」「示例模型」「另存为 GLB」三个按钮重构成两个下拉菜单（「示例模型」直接删除，不留占位）。交互跟「场景 ▾」菜单完全同款（点击展开、点外部/按 ESC 收起），三个菜单共享同一份 `registerMenu()` 基础设施，不是各自单独实现一套。

### 打开 GLB ▾
- **本地文件**——原来「打开 GLB」按钮的行为，原样保留，不依赖后端。
- **从服务器打开…**——调 `GET /api/projects.php` 拉取项目列表，弹出一个简单的选择面板（项目名 + 更新时间 + 大小）。点选某一项后：先 `GET /api/projects.php?id=<id>` 拿到详情（含 `glbUrl` 和当前版本的注释 JSON），再单独 `fetch(glbUrl)` 拉取真正的 GLB 二进制数据，然后**走跟本地打开完全同一条 `openBuf()`/`preprocess()` 代码路径**渲染出来——注释数据的接入方式是在调用 `openBuf()` 之前，把服务器返回的注释 JSON 按 `openBuf()` 内部会用的 `fileKey`（文件名 + 字节数）规则临时写进 `localStorage`，让 `openBuf()` 原有的「恢复历史注释」逻辑自然读到，没有另外写一套注释合并/覆盖逻辑。

### 另存为 GLB ▾
- **本地文件**——原来「另存为 GLB」按钮的 `GLTFExporter` 下载行为，原样保留（文案、状态栏消息都不变），只是打包逻辑抽成了一个共用的 `exportGlbBlob()`（Promise 包一层 `GLTFExporter.parse()`），供本地下载和服务器上传两边共用同一份「生成 GLB 二进制」的代码，不是两套分叉实现。
- **保存到服务器…**——用 `exportGlbBlob()` 生成的 GLB + 当前的注释 JSON，一起 `multipart/form-data` POST 给 `/api/upload.php`（字段名 `glb`/`meta`/`name`，接口约定见 `Doc/BACKEND-SPEC.md` §四/§六）。**这一轮范围只做「新建项目」**——`upload.php` 本身也只有新建这一种操作，没有带 id 的更新接口（版本历史/覆盖更新已有项目是 `Doc/BACKEND-SPEC.md` §2.3 留的第二轮范围），所以每次点「保存到服务器」都会新建一个项目，不会覆盖上一次上传的那个。

  上传成功后会拿到一个 `ownerToken`（64 位 hex，之后修改/删除这个项目要靠它，服务端只存哈希、明文只在这次 HTTP 响应里出现一次）。3AS 用一个不会自动消失的浮层（跟状态栏消息一闪而过不同）把项目 ID 和 Token 明显地展示出来，并提示"这是唯一一次显示，请立即复制保管"，`<code>` 文本框可以点一下全选、也配了「复制」按钮。**这次范围内 token 只存在内存变量里（`currentServerProject`），不做 localStorage 持久化**——跨会话（刷新页面/关浏览器）会话内 token 就丢失，是本轮明确的范围限制，不是遗漏；用户如果需要长期保留，必须自己在弹窗里复制走。

- **解包为 glTF（.gltf+.bin+贴图）**——`Doc/TODO.md` #42：跟前两项一样先用 `exportGlbBlob()` 拿到反映当前编辑状态的最新 GLB，再手动拆开 GLB 的 JSON chunk / BIN chunk，把标准 glTF 分离格式的三件套（`.gltf` 文档、`.bin` 几何缓冲区、每张贴图各自独立的文件）一起打进一个 zip 单次下载。`.gltf` 里 `images[]` 从「指向内嵌 `bufferView`」改写成「指向 `images/xxx.png` 文件」，`buffers[0].uri` 补上指向 `.bin` 文件名；只被贴图引用、抽出后不再有人用的 `bufferView` 条目会从 JSON 里清理掉（同步重新编号 `accessors[].bufferView` 的引用），但 `.bin` 文件本身**不会**重新拼装缩小——原始 BIN chunk 整体原样落盘，贴图字节仍留在里面当"死重量"，这是任务允许的简化，不追求完美最小化。打包用的是项目自己手写的最小 ZIP 打包器（只支持不压缩的 STORE 方式，`crc32`/`buildZipBlob()`），没有引入 JSZip 这类 vendor 依赖，也没有走「逐个触发浏览器下载」——因为这次的产物是"一整套包"，`.gltf` 里的相对路径引用必须精确对应磁盘上的文件位置，zip 打包能保证这点，逐个下载在这方面不够可靠。默认只针对当前激活模型。实现记录见 `Doc/EDITOR-SPEC.md` §21.1。

### 架构：静态页面 + 后端合并成同一个源
本机测试和部署都推荐用**同一个 PHP 内置服务器**同时托管 `index.html`（3AS 静态页面）和 `server/` 目录（PHP 后端 API）：`php -S 127.0.0.1:<端口> -t .`（`.` 是 3as 项目根目录，不是 `server/`）。这样前端 `fetch('server/api/upload.php')` 这类相对路径调用天然是同源请求，不需要处理跨源 CORS，部署到子目录也不用改代码。如果分成两个独立进程（静态页面用 Python，后端用 PHP 单独起在 `server/` 目录下），后端需要自己加 CORS 响应头才能被前端跨源调用，目前 `server/api/*.php` 没有内置这层。

## 简单单步撤销

状态栏「撤销」按钮实现的是 Ctrl+Z 那种单步撤销——撤销最近一步编辑，不是下面「操作脚本记录 + 重放系统」那套完整的命令模式操作日志（两者是同一批写回点上的两套独立机制，一个管"怎么撤销"，一个管"记下来以后能重放"，见下一节）。

- **机制**：一个轻量全局撤销栈 `pushUndo(label, undoFn)`，最多保留 8 步（超过自动丢最老的一条）。每条记录一个人看得懂的操作描述（`label`，显示在按钮文案和 title 上）和一个能把状态精确恢复到编辑前的函数（`undoFn`）。点击按钮 = 弹出栈顶、执行 `undoFn`。切换/重新加载模型时栈会清空（旧记录闭包指向的是上一份数据，切换文件后已经失效）。也支持键盘 Ctrl/Cmd+Z（焦点在文本/数字输入框里时不生效，避免劫持浏览器原生的输入撤销）。
- **和「还原到原始值」按钮的关系**：节点 T/R/S、包围盒旋转角等功能旁边还留着各自的「还原此字段/还原此节点」按钮，还原到的是**模型刚加载时的原始值**，跟这里的「撤销」语义不同（撤销的是**最近一步操作**，可能不是原始值），两者互不冲突、各自独立，共存不覆盖。**材质详情面板是个例外**（2026-08-06 起，`Doc/TODO.md` #27）：材质那边已经把「还原到原始值」整个换掉了，改成详情区顶部一个「还原 (N)」按钮，直接复用这里的撤销栈——按材质索引筛出属于这个材质、当前还留在栈里的编辑步骤，一次性按时间倒序全部撤销，见表1材质说明。
- **拖拽类控件的撤销粒度**：滑动条/颜色选择器一次拖拽算一步（不是每个 `input` 事件都推一条，那样栈会被中间值刷满），松开鼠标/关闭取色器时才真正提交一条撤销记录。

**已接入撤销的编辑操作**（按接入时的优先级顺序）：

1. **材质字段编辑**（baseColor / 金属度 / 粗糙度 / 自发光 / 自发光强度 / alphaMode / 双面）
2. **材质清理菜单批量操作**（fallback 重命名 / 黑色材质改色 / 缩放归一化）——批量操作影响很多材质/节点，一次撤销把这次操作动过的全部材质、全部节点都精确恢复，不是只恢复一个；三个子操作如果同时勾选执行，合并成**一条**撤销记录（不是拆成三条）
3. **创建 Instance**——撤销把新建的节点（含整棵子树）连同对应的 three.js 场景图对象一起移除
4. **节点移动/旋转编辑**——撤销粒度是单个数字输入框每次失焦提交（一次编辑一个字段算一步）
5. **贴图上传/替换/移除**——撤销恢复该材质该槽位编辑前的贴图引用（three.js 侧属性 + `raw` 侧 mapDef），不删除已经写入 `raw.images`/`raw.textures` 的条目本身（跟移除贴图的既有做法一致，避免处理索引位移）
6. **UV 变换**（移动/缩放/旋转，按材质+贴图槽分组）

**尚未接入撤销的操作**（如实列出，不是漏掉，是没做）：材质拖拽指定（画廊工具栏拖拽把材质指给某个网格，`Doc/TODO.md` #19）、包围盒生成/编辑/删除、场景整体包围盒手动覆盖开关、节点/材质/贴图的备注文字字段。这些如果需要撤销支持，可以按同一套 `pushUndo` 机制后续接入。**测量基点新增/编辑/删除/设为默认基点已经在 `Doc/TODO.md` #37（2026-08-07）接入撤销栈 + 操作脚本重放系统**，见上面「测量基点系统」一节。

## 操作脚本记录 + 重放系统

对应 `Doc/EDITOR-SPEC.md` 第 10 节、`Doc/TODO.md` #13。用途：3ds Max 那边模型改了重新导出一版新 GLB 后，不用把之前在 3AS 里做过的清理/标注动作重新手工做一遍——3AS 会把这些编辑动作记成一份「脚本」，「场景 ▾ → 模型 → 重放操作脚本」可以在新模型上重新按顺序跑一遍。

### 记录

跟上面「简单单步撤销」是同一批写回点（`pushUndo` 接入的那些位置），但记的是不同的东西：`pushUndo` 记「怎么撤销」（一个只在本次会话内有效的闭包函数），这里记的是「这次操作是什么、参数是什么」（一份可序列化的描述），追加进全局数组 `anno.script`。

**已记录的操作类型**（跟撤销系统覆盖的同一批，逐条对应）：

| `op` | 触发点 | `target` | 说明 |
|---|---|---|---|
| `editMaterial` | 材质字段编辑（baseColor / 金属度 / 粗糙度 / 自发光 / 自发光强度 / alphaMode / 双面） | 材质 | `params: {field, value}` |
| `setUvTransform` | 贴图 UV 变换（移动/缩放/旋转） | 材质 | `params: {slotKey, field, value}` |
| `setNodeTransform` | 节点移动/旋转编辑 | 节点 | `params: {T, Rdeg}`（世界空间） |
| `createInstance` | 创建 Instance | 节点 | 偏移量是固定常量，不记进 params |
| `uploadTexture` | 贴图上传/替换 | 材质 | `params: {slotKey, dataUri, mimeType, fileName}`——贴图字节直接内嵌进脚本（data URI），重放不依赖用户当时选的本地文件是否还在 |
| `removeTexture` | 贴图移除 | 材质 | `params: {slotKey}` |
| `cleanupBatch` | 材质清理菜单批量操作 | 无（全局） | `params` 就是当时勾选的 `{rename, colorMode, customHex, scaleNorm}`，重放时重新跑一遍整个批量流程 |

`target` 分三种：`{byName, kind:'node', atIndex}` 按节点名匹配，`{byName, kind:'material', atIndex}` 按材质名匹配，`{byName, kind:'basepoint', atIndex}` 按基点名匹配（`Doc/TODO.md` #37 新增，测量基点新增/编辑/删除/设为默认基点几类操作用）。`atIndex` 是记录那一刻目标所在的索引，只当"同名候选之间的优先提示"用——**真实样品 `chengdu-huagao-0801.glb` 清理前全部 17 个材质都叫「fallback Material」**（V-Ray 导出的通病），纯按名字匹配会让材质相关的脚本记录不分青红皂白全部撞车解析成材质 #0；加了 `atIndex` 兜底后，只要材质顺序没变（同一份文件重放的主场景），就能精确解析回原来那一个，顺序变了才退回「按名字找第一个」这个更弱但诚实的策略。

### 存储

`anno.script` 是现有注释对象 `anno` 上的一个字段（跟 `anno.matNotes`/`anno.sceneNote` 同一层级），导出注释 JSON 时随 `anno` 整体带出去，不需要额外的导出逻辑。同一文件重新打开（含「场景 ▾ → 模型 → 重新载入 GLB」选同一个文件）时，脚本经 `localStorage`（按 `fileKey` 持久化）保留，不会被清空——这也是「重新载入 GLB 之后重放脚本」这个核心场景成立的前提。

### 重放

「场景 ▾ → 模型 → 重放操作脚本」，流程：

1. **差异梳理**：对比脚本里出现过的节点/材质名单 vs 当前模型实际的名单，找出解析不到的目标，分组列出（一个目标可能被好几条脚本记录引用，算一组）。每组三个选项：
   - **保留**——先记着，这次重放跳过，不删除脚本记录（等以后同名节点/材质出现再自动接上）
   - **放弃**——确认这个部件/材质真的没了，从脚本里删掉这些记录
   - **重新指定**——下拉框选一个当前模型里的另一个目标，重新绑定（脚本记录就地更新，往后都生效，不是只对这次生效）
   - 没有缺失目标时跳过这一步，直接给「开始重放」确认按钮。
2. **执行**：按脚本数组原始顺序（不是按目标分组）逐条重新调用对应的编辑函数（`setMatField`/`setUvField`/`applyNodeWorldTransform`/`createInstance`/`uploadMatTexture`/`removeMatTexture`/`runMaterialCleanup`，全部是已有函数，没有另外写一套"重放专用"的写回逻辑）。找不到目标（且用户没有处理成「重新指定」）或贴图数据缺失的条目明确跳过，计入统计，不静默失败；重放过程中产生的每一步都会记进诊断日志面板（成功/跳过/失败三种都记）。重放本身不会把"重放动作"又录进 `anno.script`（内部有一个 `scriptReplaying` 标记防重复）。
3. 完成后面板显示总结：成功几条、跳过几条、失败几条。

**这次范围内的简化**（如实列出）：
- 只做了"对当前已加载模型重放当前 `anno.script`"——从外部注释 JSON 文件里单独读取 `script` 字段、应用到一个刚打开的新模型这个更完整的流程没有做（"重新载入 GLB"选**同一份**文件时脚本能自动接上是因为走的是 `localStorage` 按 `fileKey` 持久化的既有机制，不是专门为这个做的导入功能）。
- 差异梳理 UI 的「保留」选项按任务要求简化成"跳过但不删除"，没有做"以后同名节点出现自动接上"这种主动监听/重新扫描机制——用户需要再次打开重放面板才会重新判定。
- 材质拖拽指定（`Doc/TODO.md` #19）、包围盒创建/编辑/删除、测量基点相关操作没有记进脚本（跟撤销系统的已知限制范围一致）。

**上栏：详情编辑区**——选中材质后展开，字段**真正可编辑并写回**，不再是只读展示：
- **漫反射**：颜色选择器，改动实时同步到 three.js 材质的 `.color`（视口立刻看到变化）和 `raw.materials[i].pbrMetallicRoughness.baseColorFactor`
- **金属度 / 粗糙度**：滑动条（暗色风格），同步 `.metalness` / `.roughness` 和 `metallicFactor` / `roughnessFactor`
- **自发光 / 自发光强度**：颜色选择器 + 滑动条（0-10），同步 `.emissive`/`.emissiveIntensity` 和 `emissiveFactor`/`KHR_materials_emissive_strength.emissiveStrength`（强度为 1 时该扩展字段会被移除，避免导出多余数据）
- **透明模式 / 双面**：可编辑。透明模式是 `OPAQUE`/`MASK`/`BLEND` 三选一下拉框，双面是单/双面开关，映射规则照抄 three.js 官方 `GLTFLoader` 对 `alphaMode`/`doubleSided` 的处理——`BLEND` 对应 `material.transparent = true`（并把 `depthWrite` 关掉，避免半透明面自遮挡的常见渲染坑）；`MASK` 对应 `material.alphaTest`（取原有 `alphaCutoff`，未设置时用 glTF 规范默认值 0.5）；`OPAQUE` 两者都清零。双面开关对应 `material.side`（`THREE.DoubleSide` / `THREE.FrontSide`）
- **备注**：可编辑文本框，输入材质用途说明（沿用原有注释机制）

**下栏：色块画廊**（连同它上方的工具条一起，在详情区下方）——网格布局的色块卡片，每张卡片一个材质：色块（当前 `baseColor`）+ 材质名 + 索引号 `#N`。点击一张卡片选中该材质，上方详情编辑区随之刷新；选中的卡片有高亮边框。**同时视口里所有引用这个材质的网格会叠加一层品红色高亮**（`matInstances[i]` 反查全部 THREE.Material 实例，再反查场景里哪些 mesh 用了这些实例，一个材质被多个网格引用时全部高亮，不止第一个），切换选中另一张卡片时旧高亮清除、恢复原始外观。高亮是叠加在原网格上的独立发光层，不修改材质本身任何数值，导出 GLB 不受影响。画廊上方工具条现在只留一行短的材质计数（「共 N 个材质」，含 `KHR_materials_specular` 扩展时追加提示），原来那三行说明文字已经挪进上面详情区的 ⓘ 浮层。

**贴图槽合并进对应属性行（2026-08-06 起，`Doc/TODO.md` #27 重构）**：早期版本「贴图槽」是详情区最下方一整块独立分区，跟上面的属性行内容重复、用户反馈过这个布局问题。现在改成贴图入口内联在各自对应的属性行末尾：
- **漫反射行**：颜色选择器右边一个 🖼 图标按钮（有贴图时右上角带一个小圆点标记），点击就地展开这个属性的贴图上传/替换/移除 + UV 变换控件（不是跳到页面底部）
- **金属度 / 粗糙度**：两行各自都有一个 🖼 入口按钮，点开任一个都是**同一份**内容——glTF 里金属度和粗糙度本来就共用同一张 `metallicRoughnessTexture`，UI 上拆成两个入口只是方便从任一行发现，底层槽位/展开状态/贴图实例（含 three.js 侧 `metalnessMap === roughnessMap` 那条已验证过的导出坑规避）都还是同一份，不会因为 UI 拆成两行就在数据层分裂成两张贴图
- **自发光**：颜色行末尾一个 🖼 入口，点开展示的内容覆盖自发光贴图（自发光强度没有独立贴图槽，不重复放入口）

每个贴图槽展开后的内容跟以前一样：缩略图（点击触发 #26 大图预览）+ 上传/替换贴图按钮 + （有贴图时）移除贴图按钮 + 隐藏 file input；**只在该槽位当前确实有贴图时**才继续往下渲染移动 X/Y、缩放 X/Y、旋转（`KHR_texture_transform`）这组滑动条。贴图解码/写回链路（`THREE.Texture`、sRGB 色彩空间约定、`flipY`/环绕模式、`raw.images[]`/`raw.textures[]` 双写）都没有变，只是挪了摆放位置。

**「还原」按钮（2026-08-06 起）**：以前每个字段（含每个贴图槽的 UV 变换字段）各自都有一个「⟲ 还原到原始值」按钮，这次全部移除，详情区顶部只留一个**「⟲ 还原 (N)」**——N 是这个材质当前记录在案、还能撤销的编辑步数，步数为 0 时按钮禁用（灰置）。语义也变了：不再是"还原到模型刚加载时的原始值"，而是"撤销这个材质最近的编辑步骤"，直接复用简单单步撤销（#22）的撤销栈——点一次「还原」会把这个材质在撤销栈里还留着的步骤按时间倒序全部撤销，不影响其它材质/节点在栈里的记录。撤销栈是全局单一栈（8 步深），不天然区分材质，靠每条撤销记录额外挂的 `{ matIndex }` 精确筛出属于哪个材质——**这里特意没有按材质名字文本筛选**：真实样品 `chengdu-huagao-0801.glb` 全部 17 个材质原始名字都叫同一个「fallback Material」，按名字匹配会把全部材质的撤销记录混在一起（开发过程中真的踩到过这个坑，用真实样品测试时步数计数完全不对，见 `Doc/EDITOR-SPEC.md` §7 实现记录），改用材质索引后才精确。已知限制：撤销栈总共只留最近 8 步，材质编辑很多、又跟其它材质/节点操作交替进行时，这个材质更早的步骤会被挤出栈，「还原」只能覆盖"当前栈里还留着的部分"，不是"这个材质从加载以来的全部历史"。

金属度/粗糙度、自发光/自发光强度、透明模式/双面这三组字段两两并排布局（不是一个字段占一整行），滑动条本身还是滑动条、行为不变，只是纵向排布更紧凑，同样的字段数占用的面板高度比早期版本更少。

**用于节点**：详情区底部单独一块区域，列出反查到的引用该材质的节点（chip 形式），点击一个节点 chip 会跳转到「模型块」Tab 并高亮定位到对应行（自动展开被折叠的祖先节点、行短暂闪一下），**同时视口里对应节点也会出现跟节点树选中一样的青色包围框**（跟表3「点行选中节点」是同一套高亮机制，见下方表3说明）。CAD 类导出常见材质名统一为 `fallback Material`、无贴图，仅靠名称和色块难以分辨用途时，靠这块定位。

**写回链路**：编辑任何字段都会同步做两件事——① 更新场景里 GLTFLoader 实际用于渲染的 THREE.Material 实例（多个网格共享同一材质索引时，通过 `gltf.parser.associations` 反查出全部引用它的实例集合一起改，不会漏掉）；② 更新 `raw.materials[i]`（`gltf.parser.json`，材质表构建时用的原始 JSON）。「另存为 GLB」用 `GLTFExporter` 序列化的是当前 three.js 场景，读的正是被①改过的 Material 属性，因此编辑后导出的 GLB 里 `baseColorFactor` 等字段是真实改过的新值，不是原始值。

贴图 UV 变换走同一套①②模式，但多一步：`GLTFExporter` 序列化 `metallicRoughnessTexture` 时，如果 three.js 材质的 `metalnessMap` 和 `roughnessMap` 不是同一个对象引用，会触发它自己的「合并重打包」逻辑生成一张新的、变换归零的贴图，编辑过的 UV 值会在导出这一步丢失——所以编辑金属粗糙槽的 UV 时，3AS 会确保这两个属性指向同一个 clone 出来的 `THREE.Texture` 对象，规避这个导出端的坑。

贴图上传/替换/移除也是同一套①②模式：`GLTFExporter` 序列化贴图时读的是 three.js `Texture.image`（`processImage()`），不是 `raw.images[i].uri`，所以①（three.js 材质属性）才是导出正确性的关键；「另存为 GLB」用 `binary: true` 导出时，新上传的贴图数据会被重新编码进 GLB 的 BIN 二进制 chunk（`images[].bufferView` 指向内嵌数据），不是外部 `uri` 引用——用真实样品 + 手写 GLB chunk 解析验证过这一点（见下方「新版功能」测试记录）。`raw.images[i].uri` 这份 data URI 只是给 3AS 自己的贴图表/材质表二次渲染用，读取失败也不影响导出。

**用途**：
- 检查 PBR 参数是否合理（金属度/粗糙度典型值、自发光强度），发现不合理直接改
- 识别未命名材质、清理 3ds Max V-Ray 导出常见的纯黑 fallback 材质
- 确认扩展支持（高光/自发光强度）

**材质清理菜单（批量操作，2026-08-05 起）**：色块画廊工具栏「🧹 清理」按钮打开一个批量操作面板，专门对付 3ds Max V-Ray 材质导出成 GLB 后常见的「一堆 `baseColorFactor=[0,0,0,1]` 纯黑 `fallback Material`，肉眼分不清彼此」这个问题。四个操作勾选好组合后点「应用」才会真正执行（勾选框本身不触发写回，避免误触）：

- **a. Fallback 材质自动重命名**：把 `fallback Material`/`material_N` 这类占位名，按引用它的节点名批量改成能看懂的名字（比如被 `L6` 单独引用就叫「L6 材质」，被多个节点共用就取第一个引用者名字+「等N个部件」）；已经有正常名字的材质不动。
- **b / c. 黑色材质替色（二选一）**：只对 `baseColor` 接近纯黑（RGB 三通道均 < 0.05）的材质生效——**b 随机浅色**，每个黑色材质各自独立在 RGB 200-254（0-255 显示值域）随机取值；**c 指定统一色**，全部换成同一个颜色，默认 `#c8c8c8`，面板里有颜色选择器可以改这个默认色。
- **d. 缩放归一化**：把节点自身的局部缩放烘焙进它拥有的网格顶点数据（含法线按逆转置矩阵正确变换，非等比缩放下光照方向不会歪），写回后节点 `scale` 变成 `(1,1,1)`，但因为顶点坐标已经预先乘过缩放因子，世界空间外观（位置/大小）不变——常说的「Apply Scale / Freeze Transform」。只处理「自己带 mesh 的节点」，纯分组节点本身缩放不是 `(1,1,1)` 时这一轮不处理（会在结果反馈里报告跳过了几个，不假装处理了）。

a/d 可以独立勾选启用；b/c 互斥（单选，含「不处理黑色材质」这个默认选项）。写回跟材质编辑器同一套双写模式：改 three.js 对象（`Material` 实例属性 / `BufferGeometry` 顶点数据）+ 改 `raw.materials[]`/`raw.nodes[]`，执行完材质画廊、材质详情、节点表都会刷新显示新状态。跑完在状态栏和日志面板给出量化反馈，例如「已重命名 17 个材质，16 个黑色材质已改色（随机浅色）」。

**画廊工具栏（2026-08-06 起）**：色块画廊上方工具条新增视图切换 + 视口取色两组控件，跟「🧹 清理」按钮并排：

- **块视图 / 列表视图切换**（▦ / ☰ 两个按钮）：块视图是原来的网格色块布局；列表视图每行一个材质，色块缩小到 22px，横向排列「色块 + 名字 + 金属度/粗糙度/透明模式（+双面）关键参数 + 索引号」，信息密度更高，材质数量多（几十上百个）时更适合一眼扫参数而不是数色块。当前选的是哪个视图存在模块级变量里，切换 Tab、编辑材质都不会重置，但不做 `localStorage` 持久化（刷新页面/重新打开文件会回到默认块视图）。
- **贴图缩略图**：色块卡片如果这个材质的固色（`baseColor`）槽有贴图，卡片直接显示这张贴图的实际缩略图（复用材质详情区贴图槽已经在用的解码逻辑，`createImageBitmap` → canvas → dataURL），不是纯色块；没贴图的材质仍然显示 `baseColor` 纯色块。注意：这是「显示这张贴图长什么样」，不是把贴图颜色和 `baseColorFactor` 相乘算出最终着色结果——glTF 里两者是相乘关系，画廊卡片这个简化展示优先级更高的贴图纹理本身，不做实时着色计算。
- **多色材质角标**：如果一个材质除了主色（`baseColor`，即色块本身）还设了另一个非默认颜色（目前只认自发光 `emissiveFactor` 非黑），色块右上角会出现一个小圆点，颜色就是那个次要颜色，hover 有 tooltip 说明；块视图、列表视图都有，不额外占用布局空间。
- **视口取色（eyedropper）**：点「◎ 取色」按钮进入拾取模式（视口光标变十字，按钮高亮，状态栏提示），再点视口里的任意一个网格，自动定位到它当前使用的材质——画廊滚动到那张卡片、卡片短暂黄色闪烁、展开详情编辑区，同时触发跟「点色块选材质」一样的视口高亮，是「材质选中→网格高亮」的反向操作。命中一次自动退出拾取模式；也可以再点一次「取色」按钮或按 `Esc` 手动退出。内部用 `THREE.Raycaster` 从点击的屏幕坐标发射射线，命中场景里的 mesh 后用 GLTFLoader 自带的 `gltf.parser.associations` 反查表找出这个 mesh 对应的 `raw.meshes[].primitives[].material`，不需要另外维护一张反查表。
- **拖拽指定材质**：画廊卡片可以直接拖拽（原生 HTML5 drag and drop），拖到视口里的某个网格上松手，就把这个材质指派给该网格——这是真正的编辑操作，会改变这个部件用哪个材质，不只是查看。拖拽悬停在候选网格上方时，那个网格会出现一圈白色轮廓描边提示（复用材质高亮的撞色兜底描边手法，但只描当前悬停的这一个网格、不叠加发光呼吸层，比完整材质高亮更轻量）。松手时同样用 Raycaster 定位命中的 mesh，写回两处：① 把该 mesh 的 three.js `.material` 直接指向目标材质在 `matInstances` 里已有的共享实例（不新建 clone，之后编辑这个材质，这个网格也会跟着联动变化，跟项目里其它地方「材质实例共享」的既有假设一致）；② 把 `raw.meshes[meshIndex].primitives[primIndex].material` 改成目标材质索引（另存为 GLB 不读这份，纯粹是材质表/模型块表格再渲染、注释 JSON 导出跟编辑状态保持一致）。**已知范围限制**：如果多个节点原生共享同一个 `mesh` 索引（glTF instancing），这次只改被拖拽命中的那一个网格实例，不会连带改所有共享这个 mesh 索引的其它节点——真实样品没有这种共享 mesh 的情况，这个边界场景留给以后有真实需求时再扩展。

**材质/贴图大图预览弹窗（2026-08-06 起，`Doc/TODO.md` #26）**：三处点击入口共用同一套居中浮层——① 画廊色块本体（跟「点色块选中材质」是同一次点击，会顺带选中该材质，方便关掉预览后直接在下方详情区编辑）；② 材质详情编辑区每个贴图槽的缩略图（表1「贴图槽编辑区」那几个 32px 小图）；③ 表2「贴图」Tab 每一行新增的缩略图列。展示尺寸取舍：贴图长边 ≥800px 按原始像素 1:1 显示（不额外放大，避免比原图还糊）；长边 <800px 才等比放大到长边=800，给个合理的最小可视尺寸；原图特别大时弹窗本身 `overflow:auto` 允许滚动，不会把弹窗撑出屏幕。滚轮在弹窗内缩放显示比例（纯 CSS `transform:scale()`，0.1×-8×，不重新解码图片，不做拖拽平移——按需求只做缩放）。点弹窗外部区域关闭，跟设置面板/包围盒面板同一套惯例。**纯色材质降级**：如果这个材质在对应槽位没有贴图（比如色块点的是只有 `baseColor` 没有贴图的材质），弹窗改成展示一个放大的纯色块 + 文字提示「此材质没有贴图，仅有颜色 `#xxxxxx`」，不留空弹窗也不报错。表2 缩略图额外做了三级 fallback（有材质引用时复用已加载的 `THREE.Texture` 免解码；材质自己上传的贴图 `raw.images[i].uri` 是 data URI 直接可用；两者都没有的孤儿贴图现场从 GLB BIN chunk 按 `bufferView` 解码），覆盖「贴图存在但当前没有任何材质引用它」这种边界情况。**已知交互取舍**：色块点击同时承担「选中材质」和「打开预览」两个职责——块视图下色块占card绝大部分面积，点色块基本等于点卡片；如果只是想选中材质不想弹预览，可以点卡片上的名字/索引文字区域（不在色块范围内，不会触发预览）。

**三个操作（2026-08-07 起，`Doc/TODO.md` #35）**：
- **替换**：入口是「选中的贴图（`raw.images` 下标）」，反查第一个引用它的「材质索引+槽位」后转发调用材质编辑器已有的 `uploadMatTexture`（`Doc/TODO.md` #16，函数本身一行没改）。**没有被任何材质引用时按钮 disabled**，`title` 提示「未被引用，无法替换：这张贴图没有被任何材质使用，不知道要替换哪个材质槽位」——因为函数签名是按材质槽位设计的，一张孤儿贴图不知道该替换哪个槽位。跟材质编辑器里直接替换同一个效果：`uploadMatTexture` 内部总是新增一条 `raw.images`/`raw.textures` 记录再让材质槽位重新指向新索引（不是原地覆盖字节），所以替换完之后原来那张贴图会变成 0 引用的孤儿记录，继续留在列表里（跟「移除贴图」从不做索引位移垃圾回收是同一个既有原则）。
- **改名**：见上方详情区字段说明。
- **删除**：先用 `rebuildTexTable()` 已经在算的 `t.refs`（引用清单）列出全部引用该贴图的材质名单，弹二次确认浮层（跟材质清理菜单/包围盒面板同一套「居中浮层」外壳）；**同样没有被任何材质引用时按钮 disabled**，`title` 提示「没有可清空的引用」。确认后对每一处引用调用材质编辑器已有的 `removeMatTexture`（`Doc/TODO.md` #16，一行没改）——清空 three.js 材质实例对应属性（置 `null`）+ `raw.materials[i]` 对应槽位的 mapDef 引用，不删除 `raw.images`/`raw.textures` 里的条目本身。全局撤销栈（Ctrl+Z / 状态栏「撤销」）里会因此出现 N 条独立的「移除贴图」记录（N = 受影响材质槽位数），不是单条原子撤销——这是直接复用 `removeMatTexture` 既有撤销粒度的自然结果，如实记录。

**跟材质编辑器的跳转联动（2026-08-07 起，`Doc/TODO.md` #35）**：材质详情编辑器里每个贴图槽（固色/金属粗糙/法线/AO/自发光）只要当前关联了一张贴图，缩略图旁边就会出现一个「⇥ 贴图」按钮，点击切到贴图 Tab 并选中定位对应那张图（滚动到可见 + 详情区/列表行两处短暂高亮闪烁），跟「用于节点」chip 跳转材质、视口取色跳转材质画廊是同一类「跳转+定位+高亮」模式。

**批量导出全部贴图（2026-08-08 起，`Doc/TODO.md` #41）**：列表顶部（跟「共 N 张贴图」计数同一行）新增「⇓ 批量导出全部贴图」按钮，把当前模型 `raw.images[]` 全部贴图逐个下载到本地。**用逐个 `<a download>` 触发浏览器原生下载**，不是打包成 zip（两种方案的权衡：zip 需要新增 JSZip 这个通用工具库依赖，违背项目一贯坚持的「build-free、纯本地 vendor、不依赖 CDN」原则，且典型贴图数量个位数到十几张，逐个下载的用户体验代价可控——已知代价是浏览器可能对连续多次下载弹出一次性确认提示，允许一次后同一站点不会再问，已在 ⓘ 说明里如实告知）。两种贴图数据来源都处理，复用已有解码路径：① GLB 内嵌贴图走 `bufferView`，从 `currentBuf`/`currentBinOffset` 按跟 `rebuildTexTable()` 同一条公式切片；② 本工具自己上传/替换过的贴图，`raw.images[i].uri` 是上传时存的原始文件 data URI，直接 `fetch` 取回逐字节相同的原始字节，不经过 canvas 转码。**命名**：用原始文件名（`raw.images[i].name`），重名时在扩展名前插入 `(1)`/`(2)` 序号后缀防覆盖（`texture.png` → `texture(1).png`）。**没有贴图时**（`raw.images.length === 0`）按钮渲染出来但 disabled，不报错。导出过程状态栏实时显示进度（`N/总数`），完成后给出成功/失败张数汇总。

**用途**：
- 检查贴图体积（过大贴图影响加载速度）
- 确认格式兼容性（WebP/KTX2 需显式声明扩展）
- 识别未使用贴图（详情区「被哪些材质引用」为空、替换/删除按钮均 disabled）

**跟表1「材质」贴图槽编辑区联动（2026-08-05 起）**：在材质详情编辑区上传/替换贴图后，这张表会立刻多出（或替换）一行——**尺寸**是上传时 `createImageBitmap` 解码直接拿到的宽高（不用等异步解码）、**体积**是原始文件字节数、**被引用**照常反查显示是哪个材质的哪个槽引用了它。移除贴图只是清空材质那边的引用，这张表里的图片记录本身不会被删除（避免打乱其它可能共享同一张图的槽位/索引）。

### 表3：模型块（Nodes）

**上下分栏布局**：上方是「选中节点详情」常驻区（含 T/R/S 内联编辑，见下），下方是精简的两列树状列表——这是 huashu-design 评审（`Doc/2026-08-05-ui-review-panel-density.html` §02「核心列常驻+次级信息展开」）+ 单子节点组折叠需求（见下方）汇成的一次重构，之前是「一行塞 15 列」的密集表格，现在把偶尔才需要看的详细字段挪到点开才展开的详情区，列表本身只留一眼就能扫过去的核心信息。

**树状展示，显示 glTF `nodes` 里的全部节点**——网格叶子节点（挂 `mesh`）与纯分组节点（无 `mesh`、只有 `children` 的变换容器）都列出，按父子关系缩进。分组节点行标一个「组」标签。每个有子节点的行前面有一个 ▸/▾ 折叠三角，可点击展开/折叠子树，默认全展开；节点很多的大场景可以用折叠收起不关心的分支。

**单子节点组合并显示**：CAD 类导出（尤其 3ds Max）几乎每个网格叶子节点都会被单独包一层「只有 1 个孩子」的纯分组节点，树状表格如果照单全收会非常费垂直空间。列表把这种「只有唯一一个子节点的组」自动折叠成一行（不单独占行展示中间那层包装组），一直合并到遇到真正有内容的节点（网格叶子，或者 0 个/≥2 个子节点的组）才落地——2 层链、3 层链甚至更长的连续单子节点链都会被压成一行。**多子节点组维持原展开方式不变**——组和它的每个子节点各自占一行，这条折叠规则只对唯一子节点的组生效。glTF 底层数据结构完全不变，这纯粹是显示层的折叠优化；折叠/挂载点重定向逻辑本身不带任何用户可见的"这是合并行"标记——2026-08-06 起去掉了原来的「⊂合并」标签和详情区说明条，合并规则照常在背后工作，只是不再显式提示。

真实样品 `chengdu-huagao-0801.glb` 是这种结构的典型例子：28 个原始节点（14 组+14叶子，全部 14 个组都是单子节点组）合并后列表精简到 14 行。

**下方列表两列**（2026-08-06 起从 7 个独立列重排为「节点 / 信息」两列，信息列内部三行视觉分组；2026-08-07 `Doc/TODO.md` #36 打磨恢复成真正的 3 行——见下）：
- **节点**列：glTF 节点名（未命名显示 `node_N`），前面带缩进 + 折叠三角（如果有子节点，`▸` 折叠/`▾` 展开，点击切换）+「组」标签（如果是纯分组节点）；这一列同时是拖拽重新挂靠的手柄（见下方「拖拽重新挂靠父节点」）。
- **信息**列，一行内三行分组：
  1. **材质**：该节点各 primitive 引用的材质索引（色块+编号），一个节点可能挂多个材质 ID（3ds Max Multi/Sub-Object 材质按 ID 拆分 primitive 就是这种情况）；分组节点无材质，显示 `—`。**色块区域固定最大宽度、横向可滚动**（2026-08-07 `Doc/TODO.md` #36）——不同节点引用的材质数量差异很大（1 个到十几个都有），色块条原来是"多少材质占多宽"，行与行长短不一参差不齐；改成固定宽度容器，材质多的行超出部分靠 `overflow-x:auto` 横向滚动查看，行高统一，列表左右对齐干净。
  2. **显示 / 允许编辑 / 允许选中**：三个勾选框。「显示」「允许编辑」是查看器默认行为的既有字段；**「允许选中」是 2026-08-06 新增的字段**，UI 上是 `Doc/EDITOR-VIEWER-CONTRACT.md` 第三节「组锁定 `atomicGroup`」的落地——语义互为反面：勾选＝允许在查看器里单独选中/编辑这个节点（`atomicGroup:false`，默认态）；取消勾选＝这个节点被"冻结"，不能单独选中/编辑，只能作为它所属的组整体被操作（`atomicGroup:true`）。三个勾选框统一"打勾＝开放这项能力"的语义，读起来一致，不用在同一行里切换正负极性的心智模型。
  3. **别名 / 关联基点**：别名（查看器 UI 显示名）+ 关联基点下拉框（选场景里已有的测量基点，或留空用场景默认基点，详见下方「测量基点」小节）。**备注字段 2026-08-07（#36）挪进了上方详情区**——原来三个字段（别名/关联基点/备注）挤在同一行，在常见面板宽度下会被挤出视觉第二行，肉眼看列表变成 4 行而不是 3 行；备注不属于"扫一眼就要看到"的核心字段，移到详情区后列表稳定保持 3 行。

以上「显示/允许编辑/允许选中/别名/备注/关联基点」这几项注释复用同一套 `nodeAnno(name)` 机制（按节点名字存），分组节点和网格节点用法完全一样，不需要单独的注释结构；合并行则按下方「合并行注释挂载点」规则决定写到哪个名字上。

**上方选中节点详情区**：点列表里一行（选中态跟下面「选中高亮」共用同一套状态），上方常驻区展开显示这一行的详细信息；没有选中节点时显示「点一行查看详情」提示，不会报错也不会留出一块空白面板。**标题栏右侧一个 ⓘ 图标**（2026-08-07 #36，未选中节点的空状态下也在、也能点）——原来常驻在这里的一整段长说明文字（"节点树共N个节点…橙色标记的基点管理见场景Tab"，用户反馈"不要也看不懂"）收进点击后弹出的居中浮层，跟材质/贴图 Tab 的 ⓘ 说明入口同一套外壳；列表上方只留一行短计数「节点树共 N 个节点 · M 个网格块 + K 个分组」。展示内容：
- **属于**：父节点名（顶层节点显示 `—`；合并行显示的是紧邻的原始父节点，比如合并链 `node_3 → L6` 选中后显示「属于 node_3」）
- **顶点/三角**：所有 primitive 的顶点数与三角面数总和；分组节点无 mesh，显示 `—`
- **通道**：顶点属性（POSITION NORMAL TEXCOORD_0 COLOR_0 …）；分组节点显示 `—`
- **材质**：色块+编号（列表里那一列的展开版，同样固定最大宽度+横向可滚动）
- **缩放 S / 移动 T / 旋转 R°**（2026-08-06 起内联可编辑，见下方「T/R/S 内联编辑」，取代了之前的独立弹窗面板）：**世界空间**变换（沿父链累乘后分解），不是节点自身的 local matrix——glTF 导出常把网格节点包一层无名父节点承载真实摆位，只看 local 值会看到恒等/占位数据。分组节点一样有意义（子树共享的变换基），照常计算和显示。
- **相对基点**：只读展示，该节点世界坐标变换到关联基点局部坐标系后的偏移量（米）——这个值随上面「移动 T」的编辑自动联动重算，不是独立的可编辑字段（判断理由：T 才是写回 `raw.nodes` 的权威数据，相对基点坐标只是随 T 联动重算的派生视图，详见 `Doc/EDITOR-SPEC.md` §16.1）。
- **备注**（2026-08-07 #36 从列表挪过来）：节点用途说明的文本输入框，写回同一份 `nodeAnno(targetName).note`，跟列表里的别名/关联基点走同一套挂载点规则。

**合并行注释挂载点**：合并行代表一整条被折叠的链，写回注释时该挂在链顶部的包装组还是链末端的终点节点？规则是**默认挂终点节点**（它是这一行「实际代表」的东西，通常是真正的网格）；但如果链上任意一层包装组已经有非默认注释内容（说明用户之前特意在那个组的层级做过标注），就改成挂载到「最外层、已经有注释」的那个组，避免这次改版把用户已有的标注挪走、或者让编辑悄悄写到叶子上导致两条记录分裂。包围盒、T/R/S 变换这两类「针对具体节点」的操作不走这套重定向，始终对这一行的终点节点本身生效。详细规则和验证见 `Doc/EDITOR-SPEC.md` §6.2。

**选中高亮**：点击列表一行选中该节点，行背景高亮 + 视口里对应的 `THREE.Object3D` 周围出现一个黄色包围框（`THREE.Box3Helper`，颜色跟场景整体的金色边框区分开，不会混淆——2026-08-05 #25 起节点选中和材质高亮统一改成同一个黄色系 `#ffe600`，靠"线框包围盒 vs 网格表面叠加发光"两种呈现方式区分，不再靠色相区分）。选中的是分组节点时，包围框自动是整个子树的合并包围盒（`Box3.setFromObject` 天然遍历全部后代几何体求并集），不是只框某个子节点。再点一次同一行取消选中、清除包围框；切换选中别的行时旧框先消失、新框才出现，不会叠加残留。这套「节点选中→包围框」跟材质详情面板「用于节点」chip 点击共用同一套机制——两个入口，一套状态。跟材质高亮是两个独立状态，互不清除：先选材质再选节点，两种高亮会同时挂在视口里，不冲突。

**T/R/S 内联编辑**（2026-08-06 起，详见 `Doc/EDITOR-SPEC.md` §16.1；取代了之前"点按钮弹独立面板"的做法）：选中节点详情区里，缩放 S / 移动 T (m) / 旋转 R° 三组数字输入框横向并排在同一行，改完输入框失焦（或 Tab 到组外）立即提交写回——不需要额外点击"应用"按钮。**这次缩放 S 也第一次变成可编辑**（之前只有 T/R 可编辑）。写回目标是 `raw.nodes[i]` 本身（预处理阶段调整节点摆位的基线数据，不是 viewer 端终端用户的「个人方案」`UserScheme.transforms`，两者是 `Doc/EDITOR-VIEWER-CONTRACT.md` 第二节说的不同层）：原来用 `matrix` 表示的节点继续写 `matrix`，原来用 `translation/rotation/scale` 分开表示的继续分开写，不强行统一成一种格式。行尾一个「⟲」按钮一键还原这个节点的缩放/位置/旋转全部到原始值。改完立即刷新视口三维物体位置 + 详情区「相对基点」联动重算；这个节点如果正被选中（黄色包围框），包围框跟着挪到新位置。核心技术点是「世界空间目标值 → 当前父节点局部空间下应该写什么」这个转换，用 `localMatrix = inverse(parentWorldMatrix) * targetWorldMatrix` 求；写完用独立于计算过程的 `nodeWorldMatrix()` 重新读一遍该节点的世界空间 T/R/S 核对确实等于目标值。合并行同理，始终对终点节点本身生效。

**视口拖拽 gizmo**（2026-08-07 新增，详见 `Doc/EDITOR-SPEC.md` §19）：视口右侧新增一条竖排工具条（跟视口左侧「正视/侧视/顶视/默认」视角快捷按钮对称），上半组「▢选择 / ✥移动 / ↻旋转 / ⤢缩放」四选一互斥模式按钮，下半组「⬚包裹框 / ⊕中心点 / ⇩导出」三个快捷动作按钮（跟上半组不同，这三个不是模式，是点一下就触发一次的动作，见下方「视口工具条动作组」）。「选择」是默认模式，点视口物体只选中不改变任何东西；切到「移动/旋转/缩放」后，选中节点上会出现 three.js 官方 `TransformControls` 拖拽手柄——移动是三色方向箭头（红X绿Y蓝Z），旋转是三色圆环，缩放是三色方块手柄，均可直接用鼠标拖拽操作，实时改变节点的世界空间位置/朝向/大小。拖拽手柄时相机操作（`OrbitControls`）会自动临时禁用，松手后自动恢复，不会出现"想拖手柄结果转到了相机视角"的误操作。**这是上面 T/R/S 内联编辑数值输入框之外新增的第二种输入方式，两者并存、双向同步**：拖拽手柄结束后数值输入框立即刷新显示新数值；反过来在数值框里改完数字，手柄也会在视口里立即挪到新位置。拖拽结束（松手）算一次完整操作，跟数值框编辑一样接入单步撤销（`Ctrl+Z`）和操作脚本记录/重放系统。已知限制：如果一个节点的父节点自身世界缩放明显不均匀（比如某个方向被压扁成薄片），对该节点做偏离缩放主轴的旋转会因为矩阵分解的数学局限产生偏差（跟上面「拖拽重新挂靠父节点」提到的 `attach()` 已知限制是同一类现象），真实样品里这种情况占少数，不影响正常使用。

**相机视角卷展栏**（`Doc/TODO.md` #43，2026-08-08 新增，详见 `Doc/EDITOR-SPEC.md` §21.2）：视口左上角「正视/侧视/顶视/默认」4 个视角快捷按钮正下方，新增一个折叠入口「📷 视角 (N) ▾」——默认收起，不常驻占用视口空间，点击展开一个小面板，不是用 `<details>` 卷展栏那种嵌在文档流里的折叠（那种展开会推挤下面的兄弟内容，不适合浮动在视口角落的场景），而是复用 header 那三个「场景 ▾ / 打开GLB ▾ / 另存为GLB ▾」下拉菜单同一套点击展开/点外部或按 ESC 自动收起的基础设施——这就是原话「折叠在菜单内部」字面意义上最贴近的既有组件。展开后支持四个操作：

- **新建**：把当前相机的位置/朝向目标点/视野角/缩放（`camera.position`/`controls.target`/`camera.fov`/`camera.zoom`，外加 `camera.up`——多存这一项是因为「顶视」预设会把它从默认 `(0,1,0)` 改成 `(0,0,-1)`，`OrbitControls` 拖拽不会自动纠正，不存的话没法保证应用后画面精确复现）整份保存成一条新记录，默认命名"视角"/"视角2"……（撞名自动加数字后缀，防重名逻辑照抄测量基点系统的既有写法）。
- **应用**：点某条记录，相机直接跳变过去（不是渐变动画——4 个预设视角本身就是瞬间切换，没有过渡效果，这里跟着用同一套体验）。应用后列表里这一行会高亮，标记"当前生效"是哪一条；手动拖拽视口后高亮自动清除（跟 4 个预设按钮的"手动拖拽后清除高亮"是同一个既有逻辑）。
- **重命名**：改列表里的名字输入框，失焦自动保存，同样有防重名。
- **删除**：从列表里移除；删的正好是当前生效的那条，高亮标记跟着清空。

每个模型各自一份（`anno.cameraViews`，跟测量基点 `anno.basepoints` 同一个存储层级），切换模型（右上角「模型 (N) ▾」切换器）时列表自动换成新激活模型自己的记录，互不污染——已用真实样品加载两次模拟两个不同 GLB 验证过：模型 A 存的视角，切到模型 B 看不到，切回 A 还在。

**视口工具条动作组**（2026-08-07 新增，详见 `Doc/EDITOR-SPEC.md` §19.7）：下半组「⬚包裹框 / ⊕中心点 / ⇩导出」三个按钮，没有选中节点时变灰 disabled（点了也只会在状态栏提示"请先选中一个节点"，不会报错）；选中节点后启用，点击立即触发对应动作，跟上半组的模式互斥态不同，不需要保持按下的选中视觉，按下瞬间有一次颜色反馈就够。三个按钮**直接复用节点详情区已有的同名按钮/功能**，只是多了一个从视口工具条触发的入口，行为逐字节一致：
- **⬚ 包裹框** = 详情区「⬚ 包围盒」同一个函数（没有就生成默认值+展开编辑面板，已有就直接打开编辑不重新生成）。
- **⇩ 导出** = `exportSelectedNode()`（导出选中节点为独立 GLB，直接触发浏览器下载）——2026-08-07 `Doc/TODO.md` #36 起这是「导出」唯一的入口，详情区原来重复的「⇩ 导出」按钮已经去掉。
- **⊕ 中心点** = 新增的居中浮层面板，把测量基点系统的「关联」「新增」「编辑」三件事收进一个面板：① 下拉框关联当前节点到一个已有基点；② 「＋以当前节点位置新建基点」按钮，用节点当前世界坐标新建一个基点（新建后自动关联当前节点，不用再手动去下拉框选一次）；③ 面板下半部分常驻显示"当前生效基点"（关联了就是那个，没关联就是场景默认基点）的可读 X/Y/Z/朝向° 四个数字，直接在输入框里改就会保存（写回 `anno.basepoints`），视口橙色基点标记同步刷新位置。这个面板和「场景」Tab 的基点管理区域是同一份数据、同一套写回函数，改一处两边都会看到。

**拖拽重新挂靠父节点**（2026-08-06 新增，详见 `Doc/EDITOR-SPEC.md` §16.4）：把某一行的名称拖到另一行上，松手后前者变成后者的子节点——`raw.nodes[]` 的父子关系（`children[]`）和 three.js 场景图同步更新，**保持世界空间位置不变**（用 three.js `Object3D.attach()`，不是 `.add()`——后者会保持局部变换不变导致视觉上"跳"到别处，前者内部自动反算局部矩阵保持世界变换不变，这次直接复用官方方法没有自己手写矩阵反算）。拖拽悬停在合法目标行上方时有视觉反馈（整行淡黄高亮 + 提示"将成为其子节点"）；拖到自己或自己的子孙节点上会被拒绝（避免循环引用），非法目标改红字提示、浏览器同时原生显示禁止放置光标。已知边界情况：如果新父节点自身世界缩放明显不均匀（比如某个方向被压扁），`attach()` 反算局部变换时在数学上可能产生"shear"（切变），这种情况下位置依然精确保持，但旋转/缩放的分解结果可能有偏差——这是 three.js `Object3D` 用 T/R/S 三元组表示变换这个设计本身的固有限制（源码注释里也写明了），不是这次实现的 bug，真实样品里已经专门验证过这个边界情况。重新挂靠接入了单步撤销（`Ctrl+Z`）和操作脚本记录/重放系统。

**操作**（详情区按钮，选中节点后才会出现；2026-08-07 `Doc/TODO.md` #36 起精确剩 2 个）：

- **⧉ 样例复制**（2026-08-07 #36 从「⧉ Instance」改中文名，全应用范围内出现「Instance」字样的用户可见文案——按钮/状态栏提示/日志/撤销栈提示/操作脚本标签/设置面板兼容性说明——一并改掉，代码内部标识符如 `createInstance()` 函数名、`matInstances` 变量名不受影响不需要改）——创建样例复制（glTF 原生「多个 node 引用同一 mesh 索引」这个能力，不需要发明新结构，详见 `Doc/EDITOR-SPEC.md` §1、§6）。叶子网格节点：新建一个 node，`mesh` 属性指向跟原节点相同的 mesh 索引，不复制顶点/材质数据。分组节点（带子树）：新建一棵结构相同的子树（node 数量跟原树一样），子树里每个叶子节点各自引用原树对应叶子的 mesh 索引——保留了子节点粒度（每个子节点仍可单独编辑材质/显隐），几何/材质数据同样不复制。新节点一律加 `_instanceN` 后缀避免撞名（`nodeAnno` 按 `node.name` 存注释，撞名会互相覆盖，见 CHANGELOG v0.1.1 已知限制），子树里每一个新建节点都单独避重，不只是根节点。新根节点默认沿 X 轴加 2 米固定偏移摆放，方便在视口里肉眼区分新旧两份——这只是创建时的简化摆放，之后可以用详情区的 T/R/S 内联编辑再手动精确调整位置。
- **⬚ 包围盒**——生成/编辑测量包围盒（OBB，定向包围盒，详见 `Doc/EDITOR-SPEC.md` §7 末尾）。没有包围盒时点击=按该节点**世界空间**旋转角（不是节点自身 local 旋转）默认生成一个并打开编辑面板；已有时点击=直接打开编辑，不会重新生成冲掉手动改过的角度。已生成的节点按钮变成青色（`.has-bbox`）方便一眼看出哪些节点有包围盒。编辑面板可以手动改旋转角（改完自动重算尺寸/中心并重画线框）、一键重置回节点世界旋转角、删除。视口里的包围盒线框是青色虚线（跟节点选中/材质高亮的黄色、场景整体的暗金色边框都拉开区分），朝向跟着节点世界旋转对齐，不是永远正对世界坐标轴的轴对齐盒子。数据结构 `{ rotationDeg, size, center }` 存进该节点的 `nodeAnno(name).bbox`，导出注释 JSON 时自然带出去，字段定义见 `Doc/EDITOR-VIEWER-CONTRACT.md` 第六节。**这个节点的变换被 T/R/S 内联编辑改动之后，已生成的包围盒会自动清除**（朝向/尺寸不再对应新姿态，需要重新生成）。合并行点这个按钮，包围盒始终生成/编辑在这一行的终点节点上（不走注释挂载点重定向），面板标题显示的是终点节点名。

**⇩ 导出**（2026-08-07 #36 从详情区去掉，改从视口右侧工具条触发）——导出选中物体。只把这个节点（含子树）能到达的 mesh/material/贴图/accessor 数据打进一份新的独立 GLB，其余无关数据裁掉，文件名 `原文件名-节点名.3as.glb`。技术上直接把选中节点对应的 `THREE.Object3D` 传给 `GLTFExporter.parse()`——`GLTFExporter` 自己就会按需收集依赖，不用手写依赖收集算法（实测验证过：单独导出一个引用 1 个材质的叶子节点，结果 JSON 里 `materials.length === 1`，不含整档其余 16 个材质）。跟视口工具条「⇩」按钮是**同一个函数 `exportSelectedNode()`、两个入口**，行为逐字节一致（详情区原来的按钮是重复入口，删掉后功能没有缺失，见下方「视口工具条动作组」）。

**用途**：
- 标记哪些节点默认隐藏（如辅助几何体、碰撞盒）
- 标记哪些节点禁止编辑（如固定背景、标牌）
- 标记哪些节点锁定为整体（如已经摆好的组合家具，防止查看器端用户单独拆开挪动其中一件）
- 补充中文别名（glTF 节点名通常是英文或编号）
- 检查模型复杂度（顶点数过高需优化）
- 通过树状层级看清楚场景的分组结构（哪些网格属于同一个逻辑组），需要时拖拽调整这个层级

### 测量基点系统

**基点**：`{ name, position:[x,y,z], zRotation }`——`position` 是世界坐标（米），`zRotation` 是朝向角（度）。字段名字面沿用了"只绕 Z 轴"的说法，但本项目 glTF/three.js 场景是 **Y-up**（`preprocess()` 摆位逻辑、默认相机推荐值都拿 `size.y` 当高度轴），所以 `zRotation` 实际存取/可视化的是世界空间 **Y 轴**（本场景真正的竖直轴）欧拉分量，对应建筑测量里的「方位角」概念，不是完整三轴旋转——字段名保留 `zRotation` 只是跟设计文档既有措辞保持字面一致，取舍理由详见 `Doc/EDITOR-VIEWER-CONTRACT.md` 第五节。允许同时存在多个基点（比如不同楼层各自一个），存进场景级注释 `anno.basepoints`（数组）。

**GLB 原生约定（每个基点自己是怎么来的）**：模型第一次加载时按优先级探测一个默认基点种子：

1. **优先级 1**：场景里有名字是 `Origin`/`_origin`/`origin`（大小写不敏感）的节点 → 取它的世界空间 T 当 `position`、世界空间 Y 轴分量当 `zRotation`
2. **优先级 2**：没有这种命名节点 → 用现有场景表已经在算的包围盒中心（`默认中心点`）当 `position`，`zRotation` 默认 0°（真实样品 `chengdu-huagao-0801.glb` 走的是这条）
3. **优先级 3**：都没有 → 由用户在「场景」Tab 手动新增

同一份文件重新打开时保留已经保存过的基点列表，不会重新走一遍探测（避免冲掉用户手动调过的值）；「场景」Tab 另有「⟲ 生成默认基点」按钮可以随时手动再触发一次探测（追加新的一条，不覆盖已有的）。

**视口可视化**：每个基点在视口里有一个橙色标记（`#ff9d2e`，跟节点选中/材质高亮黄、包围盒青、场景整体暗金边框都拉开色相）：标准三轴参照（`AxesHelper`）+ 沿朝向方向的箭头（强调"朝向"）+ 贴地半透明圆环（标出地面投影位置）。标记尺寸按场景包围盒最大边长自适应，只 `scene.add()` 不进 `model` 子树，导出 GLB 天然不受影响。

**「场景」Tab「基准点」独立分区**（`Doc/TODO.md` #37）：列出全部基点，每行内联可编辑名字/位置 XYZ/朝向°，「删除」按钮移除（关联到它的节点自动变回"不关联"）。改名有级联——所有指向旧名字的节点关联同步改成新名字，撞名自动加数字后缀避重。整个区块套一个带明确边框的独立容器（跟上面的「包围盒」区块、下面的「整档备注」区块视觉上分开），标题栏右侧的 ⓘ 图标点开一个说明弹窗——浓缩讲清楚 GLB 原生约定的三级优先级 + 下面这条"默认基点"是怎么运作的（不是照抄设计文档里的技术性措辞）。

**基点优先级下拉：谁是「默认基点」**（`Doc/TODO.md` #37，核心功能）——这里有两层"优先级"，容易混淆，分开说：
- **第一层**是上面 GLB 原生约定的三级规则，只负责"首次加载时怎么算出一颗基点种子"，是过去时，基点一旦创建出来就不再变。
- **第二层**是"没有显式关联具体基点的节点，相对测量数值该用哪个基点算"这个问题——每个基点行右侧现在有一个下拉菜单，选「设为默认基点」就能把这一个基点指定成全局默认，**覆盖掉**第一层规则（哪怕场景里确实有 Origin 节点探测出来的基点，手动指定的也会盖过它，用户有最终决定权）。下拉框当前选中项的文字会告诉你这一行现在是不是默认、如果是靠哪条规则生效（比如「✓ 当前默认（GLB原生Origin节点）」）；不是默认的行显示「设为默认基点」这个可点击的选项。没有手动指定过的场景下，行为跟以前完全一样（fallback 到基点列表第一个）。

**基点操作的撤销 + 历史记录**（`Doc/TODO.md` #37）：新增/编辑（位置/朝向/名字）/删除基点、设为默认基点，这几类操作都接入了状态栏「↶ 撤销」按钮（`Ctrl+Z`）和「场景 ▾ → 模型 → 重放操作脚本」这套操作脚本重放系统——跟材质编辑、节点移动旋转等既有操作是同一套机制，不是另开一套。「场景」Tab 的基点列表和视口新工具条「中心点」面板共用同一份底层写回函数，接入一次两处入口都会记录。

**基点来源标注**（`Doc/TODO.md` #30，函数仍在但页面不再单独渲染成标签——`Doc/TODO.md` #37 之后来源信息并进了上面的下拉框文案里）：自动生成的基点内部记着是命中优先级 1（Origin节点）还是优先级 2（包围盒中心兜底）；用户手动新增的记着「手动创建」。

**节点关联**：模型块树每行新增「关联基点」下拉框——选场景里的某个基点，或留空使用当前默认基点（上面"基点优先级下拉"决定的那一个，任务需求"留空=不关联/用场景默认基点"里选择的实现是后者：每个节点始终显示一个直观的相对坐标，不是留空就显示空白）。关联后同一行「相对基点坐标」列显示该节点世界坐标变换到基点局部坐标系后的偏移量（先减基点位置，再乘基点朝向的逆旋转，复用 `nodeObjects`/`computeOBB` 同一套世界空间变换路线，不是另起一套）。

**导出 JSON 的 `resolvedReason` 字段**（`Doc/TODO.md` #37，只读，只在导出时计算）：每个基点导出时会带一个人类可读的 `resolvedReason` 字段，说明它现在是不是当前默认基点、如果是靠哪条规则——`"GLB原生Origin节点"` / `"场景包围盒中心（兜底）"` / `"用户手动指定为默认"`（这三种对应"是当前默认"），或者 `"非当前默认基点"`（场景里其它不是默认的基点）。**一个值得注意的边界情况**：如果 GLB 里确实有 Origin 节点探测出来的基点，但用户后来手动把另一个基点指定成了默认，那个 Origin 节点基点的 `resolvedReason` 会变成 `"非当前默认基点"`——不会因为它自己"历史上是怎么来的"没变就误报成还在生效，`resolvedReason` 回答的始终是"现在"的状态。

数据存进 `anno.basepoints`（基点列表）+ `nodeAnno(name).basepointRef`（节点关联的基点名字）+ `anno.defaultBasepointName`（手动指定的默认基点名字，`Doc/TODO.md` #37 新增），字段定义见 `SPEC.md` 的 `Annotations` 接口（`MeasurementBasepoint` 类型），GLB 原生约定探测规则/坐标系取舍详见 `Doc/EDITOR-VIEWER-CONTRACT.md` 第五节、`Doc/EDITOR-SPEC.md` §8。基点对象上额外带的 `source` 来源标注字段是纯展示元数据（不参与坐标计算，`SPEC.md` 未收录），旧注释 JSON 里没有这个字段的基点统一按「手动创建」展示。

## 注释持久化

**存储方式**：localStorage，键名 `3as:<文件名>:<字节数>`

**存储内容**：
```json
{
  "file": "model.glb",
  "updated": 1722800000000,
  "nodes": {
    "Rectangle2133441908": {
      "visible": false,
      "allowEdit": false,
      "alias": "车位 box",
      "note": "默认隐藏的占位几何体"
    }
  },
  "matNotes": { "0": "主体金属材质", "1": "玻璃透明" },
  "texNotes": { "0": "固色贴图 2K", "1": "法线贴图 1K" },
```

**自动保存**：任何输入框 `onchange` 触发保存，底部状态栏显示「注释已保存 14:32:15」

- 如需清空注释，浏览器开发者工具 → Application → Local Storage → 删除对应键

## 3ds Max 导出建议（V-Ray 场景）

**背景**：3ds Max 自带的 glTF 导出器（File → Export → glTF，底层是 Autodesk ATF → GLTFConsumer）只认识 Physical Material / Standard Surface，**不认识 VRayMtl**。场景里的材质如果还是 V-Ray 材质，导出的 GLB 里每个材质都会摊成一个叫 `fallback Material` 的纯黑色兜底材质，没有金属度/粗糙度/贴图——3AS 项目里 `glb/0A_JIMMYCHOO_CD260804.glb` 这份实测样品就是这个状况（17 个材质全是 `fallback Material`，0 张贴图）。用 3AS 打开一份 GLB 后，如果材质表里名称清一色 `fallback Material`、漫反射清一色 `#000000`、贴图表是空的，基本就能确诊是这个问题，不是 3AS 解析错了。

**推荐先试的免费/原生路线**：
1. 场景里的 `VRayMtl` 先转换成 3ds Max 原生材质再导出。Autodesk 3ds Max **2023.2 起自带 Physical Material → glTF 的转换能力**、以及独立的 **glTF Material** 材质类型（Material/Map Browser → General → glTF Material），官方发布说明见下方链接。具体菜单路径请以你安装的 3ds Max 版本为准自行核实——这一步我没有 3ds Max 环境能替你跑一遍，只能给到 Autodesk 官方文档和演示视频的线索。
2. 场景里如果用了 V-Ray 的程序贴图（噪波、渐变、VRayDirt 等非 Bitmap 贴图），glTF Material 只接受 **Bitmap 贴图**作为输入，程序贴图需要先烘焙成贴图再接上去。
3. 转换后确认材质类型确实变成了 Physical Material 或 glTF Material（而不是还挂着 VRayMtl），再执行 File → Export → glTF(.gltf/.glb)。
4. 导出后拖进 3AS 复查：材质名称不再是 `fallback Material`、漫反射不再是纯黑、贴图表不再是空的，说明材质数据被正确读出来了。

**如果原生路线太繁琐**（材质数量多、程序贴图多、手动转换成本高），备选方案：
- **V-RayMax Converter PRO**（[ScriptSpot](https://www.scriptspot.com/3ds-max/scripts/v-raymax-converter-pro)）：付费脚本，专门做 V-Ray/Corona → glTF Material 批量转换，3ds Max 2023+ 支持。
- **RapidPipeline**（[docs](https://docs.rapidpipeline.com/docs/rapidpipeline-cloud-tutorials/dcc-import)）：付费云平台，上传含 V-Ray 材质的 Max 场景，自动转 PBR + 烘焙贴图，出 glTF/GLB/FBX/USDZ，带 QC 报告；但模型会离开本机上传到云端，和 3AS「本地处理」的定位不同，仅作为对照的成熟方案参考。
- **Khronos 官方 glTF 插件**（[GitHub](https://github.com/KhronosGroup/glTF-3ds-Max-Plugin)，2026-07 由 Khronos 出资开源，Apache 2.0）：主要补上「glTF 导回 3ds Max」的能力，方便导出后再拉回 Max 核对，不是材质转换工具。

### GLB 上传政策

仓库是公开的，但 GLB 模型文件默认**不算公开可分享**——除 Chengduhuagao 案例（`chengdu-huagao-0801.glb`）外，`glb/` 目录下的其他模型默认视为 WIP / 客户监修状态，`.gitignore` 已排除，不会被 `git add` 进来。本地测试随便放文件进 `glb/` 没问题；如果确实需要把某个新样品提交进仓库共享，先跟负责人确认这份模型是否已经可以公开。HTML/CSS/JS 代码文件没有这个限制，正常提交。

## 与 Chengduhuagao 案例（3ds-viewer）的关系

> 命名统一用拼音 **Chengduhuagao**（对应文件名 `chengdu-huagao-0801.glb`）。之前文档里出现的「huagao3d」是不准确的叫法——它暗示这是一个独立的查看器产品，实际不是，见下文。

**Chengduhuagao / `3ds-viewer` 目前只是一个不带通用加载功能的固定案例**：`main.js` 里 `MODEL_URL` 硬编码指向 `chengdu-huagao-0801.glb`，没有拖拽/上传任意 GLB 的能力，配合 `save.php`/`mods.php` 验证了「查看 + 编辑 + 方案保存」这一段体验，但只能用于这一个模型，**不是一个独立的通用查看器产品**。

**未来方向**：等这套「查看 + 编辑 + 保存」体验补上通用 GLB 加载能力，就应该**完全并入 3AS**，作为 3AS 自己的「查看/编辑模式」，而不是维持成两个各自独立、靠 JSON 交接的项目。3AS 的目标形态是覆盖「预处理注释 → 查看编辑 → 方案保存」全流程的单一系统；Chengduhuagao 只是验证查看/编辑体验的参考案例，UI 交互和数据结构可以复用，但不会作为独立产品线继续存在。

**现状 vs 目标形态**：
| 阶段 | 现状 | 目标（并入 3AS 后）|
|---|---|---|
| 预处理 + 注释 | 3AS 已实现（本项目） | 3AS 的第一段模式，不变 |
| 查看 + 编辑 + 方案保存 | Chengduhuagao 案例硬编码单一模型，`3ds-viewer/` 独立代码 | 3AS 内置的第二段模式，加载任意 GLB + 对应 3AS 注释 JSON |

**数据消费方式**（Chengduhuagao 案例现有代码里的写法，并入 3AS 后接口不变）：
```js
// 3AS 注释
{
  "nodes": {
    "Rectangle2133441908": {
      "visible": false,
      "alias": "车位 box",
      "note": "默认隐藏"
    }
  }
}

// 查看/编辑模式消费（现阶段是 Chengduhuagao 案例代码，未来直接是 3AS 自己）
const anno = await fetch('model.3as.json').then(r => r.json());
model.children.forEach(part => {
  const a = anno.annotations.nodes[part.name];
  if (a) {
    part.visible = a.visible;         // 默认显隐
    if (!a.allowEdit) part.userData.locked = true;  // 锁定编辑
    partDisplayName = () => a.alias || part.name;   // UI 显示名
  }
});
```

## FAQ

**Q1：为什么不支持 glTF（.gltf + bin + 贴图文件夹）？**  
A：GLB 是单文件自包含格式，便于拖拽与传输。glTF 分离格式需额外处理文件夹结构，Phase 2 再考虑。

**Q2：贴图尺寸「…」一直不出现？**  
A：异步解码需时间，等待 1-2 秒。若仍显示「无法解码」，贴图格式可能不受支持（如 KTX2 需 basis_universal.js）。

**Q3：注释丢失了怎么办？**  
A：localStorage 与浏览器绑定，清理缓存会丢失。建议定期「导出注释 JSON」备份。

**Q4：能否在手机上用？**  
A：布局支持窄屏和横屏，具体是三档宽度断点 + 一条独立的横屏规则（`Doc/TODO.md` #38，`Doc/EDITOR-SPEC.md` §20）：
- **≥900px**：桌面布局，视口 + 右侧面板左右分栏。
- **600-900px**（竖屏平板/大屏手机）：上下分栏，视口在上（固定 40vh 高度）、面板在下（可滚动）。
- **<600px**（手机竖屏）：在上一档基础上进一步收紧——header 按钮换行、居中弹窗面板宽度收窄到 `92vw` 以内、详情区字号/内边距/输入框宽度收紧一档，避免横向溢出裁切。
- **横屏**（`max-height: 500px`，不管宽度多少）：强制切回左右分栏，面板收窄成固定宽度侧栏（约 300px，极窄横屏时按 `42vw` 进一步收紧），优先保证 3D 视口的可视高度——这条只判断可视高度，跟上面几条宽度断点是正交关系，横屏矮屏优先生效（CSS 里写在最后，同选择器特异度下后声明的规则赢）。

视口右侧的模式工具条（`#modeTools`）和左侧视角工具条（`#viewTools`）都是绝对定位挂在 `#viewport` 内部，跟侧边面板是两个不重叠的兄弟矩形，窄屏/横屏下不会被面板遮挡，不需要额外的收起交互。

大型 GLB 在移动端性能有限，仍然推荐桌面端使用。

**Q5：支持哪些 glTF 扩展？**  
A：读取所有扩展信息并显示在「场景」表中，但只解析常见 PBR 扩展（KHR_materials_specular、KHR_materials_emissive_strength）。其他扩展（Draco、KTX2）会在表中标注，但不深度解析。
